# Research: pre-rendered media and photography on the dark ground (2026-10-09)

**Status:** current. Its budget and codecs match the code. Paths under `scratchpad/` cited here were
session scratch, not kept.

Input to ADR-0006 and prototype F. Owner's decision (brief §7, 2026-10-09, after prototype E):
objects are faked with very high-resolution pre-rendered stills and video. A still appears
first and fast, a moving version loads behind it, then plays at full quality without
hurting performance. About is carried by the courtyard photo seen through a tinted lens.
Hosting is static GitHub Pages; iPhone Safari (iOS 26) matters most.

**Evidence grades.** **E** verified here: run or measured in this container on 2026-10-09
(ffmpeg 6.1.1 with x264, x265, SVT-AV1 1.7, libvpx; sharp 0.35.5 with libvips 8.18 and aom
3.15; Playwright Chromium 1194; caniuse and MDN data read at source from GitHub and npm).
**P** primary source seen through a search summary. **F** forum, bug report or secondary
write-up. **M** recollection, unconfirmed. Most websites were unreachable from here (webkit.org,
caniuse.com and github.io were blocked); GitHub raw, npm, PyPI and GitHub release assets were
reachable. **Limit:** Playwright's Chromium has no H.264 or HEVC decoder (E: `canPlayType`
returns ""), and nothing here runs WebKit. Every iOS claim below is P/F until it is checked
on the owner's iPhone (§8 checklist).

## 1. Short answer

1. **Encode against the ground, not on it.** No lossy still or video reproduced `#0a0a0b`: in
   Chromium all were 1–3 levels off on 100 % of ground pixels, a rectangle that may show on an
   OLED in the dark (E measured, M visible; §3.1). Subtracting the ground before encoding
   (it becomes black, which YUV holds exactly) and compositing with `mix-blend-mode:
   plus-lighter` made every ground pixel exact for AV1 and halved dark-area error (E). Still
   and video share the trick, so the handoff matches.
2. **Sources in order: AV1 10-bit, HEVC 10-bit `hvc1`, H.264 8-bit.** 1200² 4 s loop: 137 /
   232 / 580 KB at similar SSIM (E). Safari plays AV1 only on hardware decoders (iPhone 15 Pro+,
   M3+; E caniuse/MDN); HEVC covers every iPhone; H.264 is the net.
3. **Dark gradients need 10-bit from a 16-bit master** (8-bit encodes ring, §3.3, E), or better,
   live in CSS. The video carries the object, not the glow.
4. **On iPhone the still is the product, the video a bonus.** iOS fetches nothing before
   playback (F) and Low Power Mode rejects muted autoplay (F, WebKit 216887): set `src` only
   for the visible tab with motion allowed; a rejected `play()` means stay on the still.
5. **About photo:** AVIF `srcset` 750/1000/1500 q50 = 55/93/178 KB after a dark grade (E).
   Depth Anything V2 Small runs offline here (3.1 s CPU, E, §6.3): enough for ≤ 1 % parallax.

## 2. Progressive delivery: still → video without a flash

| Step | Mechanism | Support | Grade |
|---|---|---|---|
| Still paints first | `<img>` with AVIF, `fetchpriority="high"` on the first tab's still only, explicit `width`/`height` | `fetchpriority` Safari 17.2+, Chrome 101+, Firefox 132+ | E (MDN BCD) |
| Still is decoded before showing | `img.decode()` then fade in (avoid half-painted AVIF) | Safari 11.1+, everywhere | E (BCD) |
| Video waits | no `src` in HTML; set it from JS when the tab is shown, after `load` and idle | — | design |
| Video fetch on iOS | iOS fetches only on `play()`/autoplay; `preload` is effectively ignored, `canplaythrough` may never fire before play | iOS Safari | F (Souders 2013, WebKit bugs 180765, 197608) |
| Start | `video.muted = true; playsInline = true; await video.play()` | muted inline autoplay allowed since iOS 10 | P (WebKit "New video policies") |
| Low Power Mode | `play()` rejects with `NotAllowedError`; no JS signal for the mode | iOS | F (WebKit bug 216887, vendor docs) |
| Swap at first painted frame | `video.requestVideoFrameCallback(() => crossfade())`; fall back to `playing` + 2 rAF | rVFC Safari/iOS 15.4+, Chrome 83+, Firefox 132+ | E (BCD) |
| Crossfade | 150–250 ms opacity on the still; still and video frame 0 differ by mean 0.9/255, max 30 at edges (E, §3.2), which a short fade hides | — | E |
| Offscreen | WebKit pauses *autoplay* videos that leave the viewport; do it explicitly anyway with `IntersectionObserver` + `visibilitychange` | — | P (WebKit blog), design |
| Leaving a tab | `pause()`, then `removeAttribute('src'); load()` to free the decoder; paused videos still hold hardware decoder slots on iOS | iOS | F (WebKit bug 193449) |
| Many videos | no documented cap; one report of 32 slots on iPhone 6 and Safari crashes on iOS 26 from parallel image decodes | iOS | F |
| Data saving | `navigator.connection.saveData` is Chrome only; `prefers-reduced-data` ships nowhere; Safari has no signal | — | E (BCD, MDN) |
| Reduced motion | `prefers-reduced-motion: reduce` → never set `src`; stills only, ≤ 150 ms crossfades | everywhere | design (UX research §4) |

**Blob URL?** Playing a fully fetched blob would guarantee "downloaded before it plays", but
WebKit bugs report blob video rejected or degraded by extra range requests (F). Use the plain
URL; clips this small buffer within a second. Revisit only if the device test stalls.

**Loop seams.** Render N frames of a cycle with frame N = frame 0 *excluded* (verified: 120
frames, exactly 4.000 s, E). Our x264/x265 files carry an `elst` edit list for B-frame delay
(E); Safari has handled edit lists differently from Chrome (F, W3C media list). If a seam
shows on the iPhone, re-encode with `-bf 0` (costs ~10–20 % size, M) before anything clever.
Put the seam on a rest pose and make loops 6–10 s so it is rare.

## 3. Experiments (Chromium, E)

Test material: 120 frames, 1200², a Recto poster rotating ±4° over a pulsing dark glow, on
exact `#0a0a0b`. Scripts and outputs were in the scratchpad (`media-research/`), not committed.

### 3.1 Black level: what the page actually shows

Screenshot diff against the PNG master, at 600 CSS px. "Ground px off" = share of pixels that
are exactly the ground in the master but not on screen.

| Media | Size | Dark px mean err | Ground px off | Ground max err |
|---|---|---|---|---|
| WebP q82 (current posters: their ground reads 10,10,10, not 10,10,11) | 26 KB | 1.09 | 100 % | 3 |
| AVIF q60 4:4:4 10-bit | 15 KB | 1.04 | 100 % | 1 |
| JPEG q85 4:4:4 | 58 KB | 0.68 | 100 % | 1 |
| VP9 / AV1 8 / AV1 10, normal blend | 210 / 141 / 137 KB | 1.0–1.2 | 100 % | 1–3 |
| **AV1 ground-subtracted + `plus-lighter`** | 143 KB | **0.56** | **0 %** | 0 |

Why: 8-bit limited-range BT.709 cannot encode (10,10,11): the blue step per chroma code is
about 2 levels, so the codec lands on (10,9,12) or (10,10,10) (E, ffmpeg decode). Pure black
is Y = 16, and encoder noise below 16 clamps to 0, so a black ground is exact.

`lighten` looked exact too, but with a subtracted encode it computes max(orig − G, G), which
crushes glow values between G and 2G: wrong. Use `plus-lighter` (additive, defined, supported
Safari 9.1+/iOS 9.3+, Chrome 100+, Firefox 99+: E, BCD). Caveat: WebKit bug reports of repaint
glitches with blend modes over video (F, bugs 286619, 235106); this is check #1 on the iPhone.

**Isolation gotcha (E):** if any ancestor between the media and the ground forms a stacking
context (`opacity < 1`, `transform`, `filter`, `isolation`) without painting the ground
itself, the blend happens against transparency and the ground turns pure black (measured:
corner 0,0,0). Page transitions animate exactly those properties. Rule: the element that
fades or moves paints `background: var(--ground)` itself.

**Side effects of additive compositing:** pixels the render had darker than the ground are
lifted to the ground (deep contact shadows lose ≤ 4 % of range; render shadows as a separate
multiply layer if they matter); anything behind the object (a project glow, the aura) adds
to it, which reads as light passing through glass and needs no extra work.

### 3.2 Still → video handoff

AVIF 10-bit still of frame 0 (subtracted, 15 KB) vs the AV1 video's first frame, both with
`plus-lighter`: mean 0.88/255, max 30 at high-contrast edges (E). WebP q90 still: mean 0.80.
Both codecs differ from the master by about as much as from each other, so the error is codec
noise, not a colour shift. A 150–250 ms crossfade is enough; a hard cut may show a shimmer.

### 3.3 Banding in a dark glow (10→36 levels, 960², 2 s)

Measured as the longest flat run (0.25-level resolution) and distinct levels along a radius;
master (8-bit dithered) = 7 px, 79 levels. Amplified ×8 by eye the same ranking held.

| Encode | Size | Longest flat run | Levels | Verdict |
|---|---|---|---|---|
| H.264 CRF 20 8-bit | 47 KB | 35 px | 53 | rings |
| H.264 CRF 20 `-tune grain` | 35 KB | 36 px | 40 | rings (encoders smooth dither away) |
| HEVC CRF 24 8-bit | 18 KB | 31 px | 58 | rings |
| AV1 CRF 32 8-bit | 4 KB | 35 px | 20 | worst |
| **HEVC CRF 24 10-bit from 16-bit master** | 16 KB | 14 px | 75 | smooth |
| **AV1 CRF 32 10-bit from 16-bit master** | 6 KB | 14 px | 70 | smooth |

Browsers do not play 10-bit H.264 (High 10), so the H.264 fallback will band; art-direct
around it (glow in CSS, object only in the video). AV1 film-grain synthesis (`film-grain=8`)
did not help the ground (max error 3) and is not worth it here (E).

## 4. Codec support (2026)

| Codec | iOS Safari 26 | macOS Safari 26 | Chrome | Firefox | Grade |
|---|---|---|---|---|---|
| H.264 (mp4) | yes | yes | yes | yes | E (caniuse) |
| HEVC (`hvc1`) | yes, all devices | yes | "partial": macOS 11+, Android 5+, Windows/Linux with hardware | 137+: hardware only, sometimes software | E (caniuse notes) |
| AV1 | only with a hardware decoder: iPhone 15 Pro, iPhone 16 and later; `canPlayType` says "" elsewhere | M3 and later | yes | yes | E (caniuse note #4, MDN) |
| VP9 (webm) | yes since 18, no alpha | yes | yes | yes | E (caniuse) |
| AVIF still | yes (16+) | yes | yes | yes | E |
| WebCodecs `VideoDecoder` | 16.4+, full WebCodecs 26 | 16.4+ | 94+ | 130+ | E (BCD, caniuse) |

Write HEVC with `-tag:v hvc1` (Apple players refuse `hev1`, M) and give every `<source>` a
`type` with a codecs string so Safari without AV1 hardware skips the AV1 file instead of
downloading it. Tag colour explicitly: untagged files make Safari guess (Gigazine test, F) and
Firefox has ignored tags (Mozilla bug 1783458, F). Chrome treats the BT.709 transfer as sRGB
(Chromium developer on FFmpeg trac, F); Safari's handling of BT.709 transfer differs (ASWF
wiki, F). Our ground trick removes the ground from the problem; for object colours, compare
still vs video on the iPhone and, if Safari shifts, try `-color_trc iec61966-2-1` (P/F).

## 5. Pointer lean, scrubbing and Apple-style sequences

| Approach | Cost (21 frames, 800², E) | Seek | Memory when decoded | Fit |
|---|---|---|---|---|
| 21 separate AVIF 10-bit q60 | 178 KB, 21 requests | instant (pre-decoded `ImageBitmap`) | 21 × 2.56 MB = 54 MB | desktop |
| One 7×3 AVIF sprite at 400² per cell | 75 KB, 1 request | instant (`drawImage` sub-rect) | 13 MB | **phones, lean** |
| H.264 GOP video, seek `currentTime` | 72 KB | async, lands on keyframes | low | no: seeking lags |
| H.264 all-intra | 370 KB | every frame a keyframe; still async | low | scrub clips |
| WebCodecs decode to `ImageBitmap` | as video | frame-exact, but demux (MP4Box) + bookkeeping | as bitmaps | later, if needed |

- **Apple** has drawn scroll sequences from per-frame JPEGs onto a `<canvas>` (the 2019 AirPods
  "hero-lightpass", 147 frames, via a third-party copy: F); scroll-scrubbed video with dense
  keyframes is the other common method (F: muffinman.io, hontran.dev). Current apple.com
  internals were not verified.
- **Lean recipe:** pre-decode the grid to `ImageBitmap`s, map pointer (or tilt) to fractional
  (u, v), draw the nearest two or four frames with bilinear opacity weights on one canvas,
  ease toward the target per frame (critically damped, ~120 ms). Crossfading neighbours hides
  stepping at 5–7 columns when the angle step is ≤ 2–3° (F: "1–3° per frame" guidance; X2 in
  `2026-10-3d-quality.md` decides). Optical-flow interpolation (ffmpeg `minterpolate`, RIFE)
  smears glass and refractions; render more frames instead (M).
- **Phones:** decoded memory is the limit, not bytes: keep the grid at ≤ 600² per cell
  (21 × 1.44 MB = 30 MB) and only for the visible tab. Gyroscope needs
  `DeviceOrientationEvent.requestPermission()` from a click on iOS 14.5+ over HTTPS (E BCD; F
  for the click-not-touchstart detail): offer it as an opt-in, never prompt on load, low-pass
  the angles, and keep the still as the default.

## 6. Photography on a dark site

### 6.1 Delivery (courtyard photo, 1500×2000 source, E)

| Width | AVIF q50 4:2:0 | AVIF q62 4:4:4 | WebP q75 | JPEG q78 | AVIF q50 after dark grade |
|---|---|---|---|---|---|
| 480 | 37 KB | 63 KB | 69 KB | 65 KB | — |
| 750 | 90 KB | 150 KB | 166 KB | 160 KB | 55 KB |
| 1000 | 146 KB | 236 KB | 263 KB | 271 KB | 93 KB |
| 1500 | 275 KB | 444 KB | 483 KB | 562 KB | 178 KB |

Foliage is expensive; grading it down 1.6 stops with a vignette into the ground cut AVIF by
35–40 %. Markup: `<picture>` with AVIF then WebP `srcset` 750w/1000w/1500w, `sizes` matching
the layout (e.g. `(min-width: 1100px) 40vw, 100vw`), `width`/`height`, `decoding="async"`,
`loading="lazy"` unless About is the landing tab. A 390 px phone at DPR 3 picks ~1170w → the
1500w file; cap at 1500w (the source is 1500 px wide; ask the owner for the original).

### 6.2 Grading into the ground (technique, taste goes to the owner)

- Grade in linear light: exposure down, saturation −10–20 %, a vignette that reaches the
  ground at the edges, then clamp to never fall below the ground and add sub-LSB dither
  (σ ≈ 0.6/255) before 8-bit quantisation. Prototype at `media-research/photo/graded.png` (E).
- Let the tinted lens rim and blurred fingers frame the image; they already read as a layer.
- Grain: one static, tiled noise texture over the whole page at 3–5 % opacity hides banding in
  CSS gradients and ties photo and renders together (M). Animated grain costs battery; avoid.
- What reads cheap (M, consistent with craft audit): a hard rectangle of grey-black against the
  ground, oversharpened foliage, HDR-looking clarity, Ken Burns zooms that loop, parallax with
  visible stretching at edges, and photos lighter than the type. Prefer no Ken Burns; at most a
  one-time 1.00→1.03 settle over 1.2 s on entry, still under reduced motion.
- The photo shows distant passers-by; they are not identifiable at this size, but crop or blur
  any face that becomes legible at 1500w (CLAUDE.md privacy rule).

### 6.3 2.5D depth parallax from one photo

- **Depth Anything V2 Small runs offline here (E).** Hugging Face is blocked, but the ONNX
  export on GitHub releases is reachable: `fabio-sim/Depth-Anything-ONNX` v2.0.0
  `depth_anything_v2_vits.onnx`, 99.4 MB, sha256 `d2b11a11…62be`; `onnxruntime` 1.31 from
  PyPI; 518×518 input, 3.1 s on CPU. The Small model is Apache-2.0; Base/Large are
  CC-BY-NC-4.0 (P). `onnxruntime-node`'s postinstall download failed (E), so use Python.
- **Result on the courtyard:** the fingers dominate the range (near = white); stretched within
  the scene, the lawn falls off correctly and tree masses separate from the sky, but edges
  are soft at 518² and foliage–sky borders are ragged (E, looked at). Usable for a gentle
  depth shader (UV offset = depth × pointer, ≤ 1 % of width), not for a camera move.
- **Cheaper and cleaner:** two hand-cut layers, lens rim + fingers in front, courtyard behind,
  moved 4–8 px by pointer with CSS transforms. No WebGL, works on phones, no stretching. The
  depth map can still drive a subtle blur or light falloff. Still twin: the flat photo.

## 7. Budget and GitHub Pages behaviour

| Bucket | Target | Basis |
|---|---|---|
| First paint (HTML, CSS, fonts, first still) | ≤ 200 KB, still ≤ 60 KB | posters measured 15–33 KB AVIF/WebP at 1200² (E) |
| Per tab, deferred: still + loop video | ≤ 450 KB AV1/HEVC, ≤ 1.1 MB H.264 | §3.4 (E) + 1.5–2× for real renders (M) |
| Lean grid (if used) | ≤ 100 KB phone sprite, ≤ 250 KB desktop | §5 (E) |
| About photo | ≤ 180 KB at 1500w | §6.1 (E) |
| Full visit, every tab opened | ≤ 3 MB | 6 tabs × ≤ 450 KB |
| Whole `media/` folder in the repo | ≤ 150 MB (3 codecs × sizes × objects, plus history) | site limit 1 GB, repo 1 GB recommended, files < 100 MB, no LFS |

GitHub Pages (E, `github/docs` source): published site ≤ 1 GB, soft bandwidth 100 GB/month,
deployments time out after 10 min, rate limiting answers 429. 100 GB at 3 MB per full visit is
~33 000 full visits a month. Every response carries `Cache-Control: max-age=600` with ETag
and Last-Modified (F: long-standing reports; no custom headers possible). Implications:
after 10 minutes each asset costs a revalidation round trip (304) on the next visit, so fewer,
larger files beat many small ones (sprite over 21 frames; one video per tab); content-hashed
names still help, because a changed file can never be served stale past 10 minutes, and they
let an optional service worker cache `media/` cache-first. Safari needs byte-range (206)
answers for video (F: GitLab Pages issue 504); GitHub Pages serving 206 is believed but not
verified here (github.io blocked): check with `curl -r 0-1` once deployed. Git history keeps
every re-encode forever: commit media only when final, and keep masters out of the repo.

## 8. Rules for ADR-0006 and the pipeline

1. Every object ships a still that is complete on its own; video is progressive enhancement.
2. Masters are 16-bit PNG (or EXR) frames rendered on the exact ground; the ground is then
   subtracted in sRGB code values (`v = max(0, px − (10,10,11))`), and both still and video are
   encoded from the subtracted master.
3. Still and video are drawn with `mix-blend-mode: plus-lighter`, and whichever ancestor fades
   or transforms paints `background: var(--ground)` itself.
4. Video sources, in order: AV1 10-bit mp4, HEVC Main 10 `hvc1` mp4, H.264 High 8-bit mp4, each
   with a codecs `type`; all tagged BT.709, limited range, `+faststart`; no audio track.
5. Wide glows and gradients live in CSS, not in video; video carries the object.
6. No `src` until the tab is visible, motion is allowed and (Chrome) Save-Data is off. Then
   `muted`, `playsinline`, `loop`, `play()`; on rejection stay on the still, silently.
7. Swap on the first `requestVideoFrameCallback`, 150–250 ms crossfade; pause offscreen and on
   `visibilitychange`; release the source when the tab is left; at most one playing video.
8. Loops: 6–10 s, frame N excluded, seam on a rest pose. Lean grids: sprite sheets, ≤ 600² per
   cell on phones. Scrub clips: all-intra, short, rendered at display size.
9. Photos: AVIF + WebP `srcset` 750/1000/1500, graded into the ground with dither, static page
   grain, no looping Ken Burns; parallax only by hand-cut layers or a ≤ 1 % depth shader.
10. Before ADR acceptance, on the owner's iPhone: (a) `plus-lighter` over a playing video, no
    glitches; (b) ground seamless around still and video, in a dark room at full brightness;
    (c) Low Power Mode on: still stays, no play button, no console noise; (d) loop seam;
    (e) still → video colour match; (f) six tabs visited twice without a reload or crash;
    (g) `curl -r 0-1` returns 206 from Pages.

### Recipe

```sh
G="10,10,11"   # page ground, sRGB code values
# 1. Subtract the ground from 16-bit frames (sharp; masters stay out of the repo)
node -e 'const s=require("sharp"),[r,g,b]=process.argv[3].split(",").map(Number);
  s(process.argv[1]).linear([1,1,1],[-r*257,-g*257,-b*257]).toColourspace("rgb16")
  .png().toFile(process.argv[2])' in/f0001.png sub/f0001.png "$G"   # loop over frames
#    verified on a 16-bit PNG: ground → 0,0,0, others shift by exactly 2570 (E). Offsets
#    are ×257 for 16-bit input only; an 8-bit master takes [-r,-g,-b]. Read 16-bit values
#    back with .toColourspace("rgb16") or ffmpeg, or sharp reports them as 8-bit.
# 2. Shared ffmpeg settings
IN="-framerate 30 -i sub/f%04d.png"
VF="-vf scale=1600:1600:flags=lanczos:out_color_matrix=bt709:out_range=tv"
TAG="-colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv -an -movflags +faststart"
# 3. Three codecs
ffmpeg $IN $VF -c:v libsvtav1 -preset 4 -crf 30 -pix_fmt yuv420p10le $TAG obj-1600.av1.mp4
ffmpeg $IN $VF -c:v libx265 -preset slow -crf 22 -pix_fmt yuv420p10le -tag:v hvc1 $TAG obj-1600.hevc.mp4
ffmpeg $IN $VF -c:v libx264 -preset slow -crf 20 -profile:v high -pix_fmt yuv420p $TAG obj-1600.h264.mp4
#    phone size: same with scale=800:800, AV1 CRF 32 / HEVC CRF 24 / H.264 CRF 21
#    scrub clip: add -g 1 (H.264 only), keep it short and at display size
# 4. Still = frame 0 of the subtracted master
node -e 'const s=require("sharp");for(const w of [600,1200,1600])
  s("sub/f0001.png").resize(w).avif({quality:60,effort:6,bitdepth:10,chromaSubsampling:"4:4:4"})
  .toFile(`obj-${w}.avif`)'
# 5. Photo
node -e 'const s=require("sharp");for(const w of [750,1000,1500]){
  s("graded.png").resize(w).avif({quality:50,effort:6}).toFile(`about-${w}.avif`);
  s("graded.png").resize(w).webp({quality:75,effort:6,smartSubsample:true}).toFile(`about-${w}.webp`)}'
```
